# Синхронизация и аккаунты: дизайн

Сервер на Ktor + Kormium, который даёт stramus аккаунт и синхронизацию между устройствами
(веб-версия ↔ расширение ↔ второй компьютер). Документ описывает, что мы строим и почему;
код по нему ещё не написан.

## Решения, от которых пляшет всё остальное

| Вопрос | Решение |
| --- | --- |
| Модель синхронизации | LWW по строкам + базовая версия + tombstones + конфликтующая копия для заметок |
| Порядок (позиции) | Дробный индекс (строковый ключ) вместо сплошной целочисленной нумерации |
| Авторизация | Email + пароль **и** одноразовый код на почту; Google OAuth — позже, схема к нему готова |
| Что синхронизируем | Всё: секции, коллекции, карточки, файлы, usage, иконки |
| PIN-секции | Синхронизируются как есть: сервер видит содержимое, PIN остаётся замком от чужих глаз за вашим экраном |
| БД сервера | SQLite (`kormium-sqlite`), файл на диске |

### Главный инвариант: оффлайн работает всегда

Сервер — **необязательное дополнение, а не источник истины**. Локальная SQLite остаётся тем,
из чего UI читает и во что пишет; синхронизация — фоновая задача поверх неё. Из этого следуют
правила, которые нельзя нарушать ни в одном месте кода:

- ни одна операция UI не ждёт сети: сохранение карточки завершается записью в локальную базу;
- нет аккаунта — приложение ведёт себя ровно как сегодня, синк просто выключен;
- сервер лежит, сеть отвалилась, токен протух — всё продолжает работать, изменения копятся
  локально и уезжают, когда связь вернётся;
- удалить аккаунт (или выйти) можно, не потеряв данные: они остаются в локальной базе.

## Откуда взята модель

Google Drive и Яндекс.Диск делают ровно это. У Drive клиент берёт курсор
(`changes.getStartPageToken`), крутит `changes.list(pageToken)` и получает изменения по порядку,
включая удаления (флаг `removed` — то есть tombstone едет как запись, а не как отсутствие записи).
Содержимое Drive не сливает: конкурирующие правки становятся ревизиями, побеждает последняя.
Яндекс.Диск держит для каждого объекта три состояния — local, remote и **stable (последнее
успешно синхронизированное)** — и при расхождении обоих создаёт конфликтующую копию.

Из этого мы забираем две идеи: **курсор + дельта с tombstones** (Drive) и **базовую версию,
позволяющую отличить настоящий конфликт от простого «изменено с одной стороны»** (Диск).
Настоящий merge (OT/CRDT) есть у Google Docs, а не у Drive — и нужен он для совместного
редактирования, которого у нас нет.

## Модули

```
core        (KMP: js + jvm)   модели, интерфейсы репозиториев, дробный индекс, правила слияния
protocol    (KMP: js + jvm)   DTO протокола (kotlinx.serialization), общие для клиента и сервера
sync        (js)              движок синхронизации: очередь, push/pull, применение дельты
server      (jvm)             Ktor + kormium-sqlite + kormium-migrate + kormium-ktor
ui-shared   (js)              + экран входа, индикатор синка, разрешение конфликтов
```

`core` сегодня существует только в `jsMain`. Его надо развести на `commonMain` (модели, интерфейсы
репозиториев, чистые функции — дробный индекс и правила слияния) и `jsMain` (реализация поверх
`kormium-sqlite-js`). Выигрыш не только в переиспользовании: **правила слияния и арифметика дробного
индекса становятся тестируемыми на JVM** — сегодня в проекте нет ни одного теста, а это ровно тот
код, который обязан быть покрыт.

## Локальная схема: что добавляется

В каждую синхронизируемую таблицу (`sections`, `collections`, `card_sections`, `cards`, `usage`,
`action_usage`, `favicons`):

```sql
"updatedAt" text NOT NULL   -- когда строку последний раз меняли, ставит клиент
"deletedAt" text            -- tombstone: NULL = жива
```

Плюс две служебные таблицы:

```sql
CREATE TABLE "sync_meta" (      -- база (stable) для каждой известной серверу строки
    "tbl"     text NOT NULL,    -- имя таблицы
    "rowId"   text NOT NULL,    -- id строки
    "hash"    text NOT NULL,    -- SHA-256 канонической сериализации строки на момент синка
    "rev"     integer NOT NULL, -- ревизия сервера, в которой эта версия приехала
    PRIMARY KEY ("tbl", "rowId")
);

CREATE TABLE "sync_state" (     -- один ряд на устройство
    "k" text PRIMARY KEY,       -- lastRev | deviceId | userId | ...
    "v" text NOT NULL
);
```

**Почему хеш, а не копия строки, и не флаг `dirty`.** Базовая версия нужна ровно для одного
вопроса: «отличается ли текущая строка от той, что сервер подтвердил?» Хеша для этого достаточно, а
копия строки удвоила бы базу (заметки, превью файлов). Флаг `dirty` тоже отвечал бы на этот вопрос,
но врал бы в двух случаях: правка с последующим откатом остаётся «грязной» навсегда, а падение между
записью строки и записью флага теряет изменение. Хеш вычисляется из данных и не может разойтись с
ними.

`"изменено локально" = hash(текущая строка) != sync_meta.hash`. Новая строка — та, которой нет в
`sync_meta`.

**Tombstones заводятся только при включённом синке.** Пока аккаунта нет, удаление остаётся
физическим (как сегодня), иначе у офлайн-пользователя вечно копится мусор. При первом входе в
аккаунт клиент делает полный push (`since = 0`) — всё, что лежит локально, объявляется новыми
строками.

Undo не меняется: `DeletedCollection`/`DeletedSection` как были снимком в памяти, так и остаются;
восстановление просто пишет строки обратно с `updatedAt = now` и `deletedAt = NULL`, и по LWW
выигрывает у уехавшего на сервер удаления.

## Дробный индекс вместо `position: Int`

Сегодня `CardRepository.move` перенумеровывает все карточки коллекции, а
`CollectionRepository.move` — все коллекции всех секций одним глобальным счётчиком
(`core/.../db/Store.kt`). При построчной синхронизации это значит, что перетаскивание одной карточки
делает изменёнными сотню строк, и встречное перетаскивание на втором устройстве даёт конфликт по
каждой из них.

Замена: `position` становится строкой — ключом, который всегда можно вставить между двумя соседями
(`"a0"`, `"a0V"`, `"a1"`, …). Перемещение трогает **одну** строку: ей присваивается ключ между
предыдущим и следующим элементом.

```kotlin
// core/commonMain — чистая функция, тестируется на JVM
fun between(prev: String?, next: String?): String
```

Сортировка — по `(position, id)`: `id` разрывает ничью, если два устройства независимо породили
одинаковый ключ. Уникальность не требуется.

Заодно чинится сегодняшняя странность: порядок коллекций перестаёт быть глобальной сквозной
нумерацией и становится порядком **внутри секции**, а порядок карточек — порядком внутри группы
(`collectionId`, `cardSectionId`). Это то, чем они и являются по смыслу.

Что придётся тронуть: `move`/`reorder` во всех четырёх репозиториях, сортировки в `CardSort.kt` и
`TabSort.kt`, миграция локальных баз (новая колонка, заполнить в текущем порядке, читать из неё).
Это самая объёмная часть всей работы, и она целиком на клиенте — сервер к типу `position`
безразличен, он для него просто поле.

## Протокол

Bearer-токен в `Authorization`. Всё под `/v1`.

### Дельта

```
POST /v1/sync
{
  "deviceId": "…",
  "since": 41,                      // 0 = первый синк, отдать всё
  "rows": [                         // строки, изменённые локально
    { "tbl": "cards", "id": "…", "updatedAt": "…", "deletedAt": null,
      "collectionId": "…", "title": "…", "position": "a0V", "blobSha": null, ... }
  ]
}

→ 200
{
  "rev": 57,                        // новый курсор клиента
  "accepted": ["…", "…"],           // id строк, принятых сервером как есть
  "rows": [ … ],                    // чужие изменения с rev > since (включая tombstones)
  "conflicts": [                    // строки, где изменилось и там, и здесь
    { "tbl": "cards", "id": "…", "server": { … } }
  ],
  "hasMore": false                  // дельта постранична; курсор — rev
}
```

Ревизия — монотонный счётчик **на пользователя** (`user_seq`), а не глобальный: один push = один
`rev`, присваиваемый всем записанным в нём строкам. Дельта — `WHERE userId = ? AND rev > ?`.

### Файлы

Байты никогда не едут в JSON. Карточка везёт `blobSha` — SHA-256 содержимого; сам блоб
адресуется контентом:

```
PUT  /v1/blobs/{sha256}     тело — сырые байты, Content-Type файла
GET  /v1/blobs/{sha256}     → байты
POST /v1/blobs/check        { "sha": [...] } → { "missing": [...] }
```

Клиент, увидев в дельте карточку с незнакомым `blobSha`, качает блоб; создав файл локально —
сначала спрашивает `check`, потом заливает недостающее. Адресация по содержимому даёт дедупликацию
бесплатно (один и тот же PDF в двух коллекциях — один блоб) и делает загрузку идемпотентной.

Лимиты: 10 МБ на файл, 500 МБ на пользователя (в конфиге). Превышение — `413`, и клиент показывает
это в UI, **не ломая локальную карточку**: файл остаётся на устройстве, просто не уезжает.

## Слияние

Для каждой присланной строки сервер смотрит на свою версию:

1. **Своей строки нет** → вставить. Новая карточка.
2. **Своя строка есть, но её `rev <= since`** — то есть с последнего синка клиента сервер её не
   менял → быстрое применение, конфликта нет. Это подавляющее большинство случаев.
3. **Своя строка есть и её `rev > since`** — изменилась и там, и здесь → **настоящий конфликт**.
   Побеждает больший `updatedAt`; при точном равенстве — больший `deviceId` (произвольное, но
   детерминированное правило: важно, чтобы оба устройства пришли к одному ответу). Строка попадает
   в `conflicts` ответа вместе с серверной версией.

Именно шаг 2 — тот, ради которого нужна базовая версия. Без неё пункты 2 и 3 неразличимы, и LWW
молча съедает одну из версий в ситуации, которая конфликтом вообще не была.

**Конфликтующая копия — только для заметок.** Получив конфликт по карточке с `kind = note`, клиент
принимает серверную версию, а свою проигравшую сохраняет **новой карточкой рядом** — с тем же
телом и заголовком вида `«Название (конфликтующая копия)»`. Новая карточка на следующем push уедет
на сервер как обычная. Логика живёт на клиенте: сервер не знает базовой версии клиента и не должен
знать. Для всего остального — заголовков, позиций, флагов — LWW честно достаточен: там теряется
одно слово, а не абзац текста.

**Счётчики сливаются иначе, чем LWW.** `usage` и `action_usage` — не значения, а счётчики: LWW
взяла бы `hits` победителя и потеряла бы открытия, сделанные на другом устройстве. Правило для этих
двух таблиц — **поэлементный максимум**: `hits = max(a, b)`, `lastUsedAt = max(a, b)`, `title` — от
более свежего. Это не идеальный CRDT-счётчик (два устройства, независимо накрутившие по +5, дадут 5,
а не 10), но он монотонен и ничего не теряет из уже учтённого — для ранжирования поиска этого хватает
с запасом, а честный per-device счётчик раздул бы таблицу.

**Часы клиента.** `updatedAt` ставит клиент, а значит устройство со сбитыми часами могло бы выигрывать
все конфликты навсегда. Сервер защищается: `updatedAt`, ушедший в будущее больше чем на 5 минут
относительно серверного времени, подрезается до серверного.

## Схема сервера

Аккаунты:

```sql
users(id uuid pk, email text unique, passwordHash text null, emailVerified int, createdAt)
identities(userId, provider, subject, unique(provider, subject))   -- задел под Google/GitHub OAuth
devices(id uuid pk, userId, name, lastSeenAt)
refresh_tokens(id, userId, deviceId, tokenHash, issuedAt, expiresAt, revokedAt, replacedBy)
login_codes(email, codeHash, expiresAt, usedAt, attempts)          -- одноразовые коды на почту
user_seq(userId pk, rev)                                           -- курсор-счётчик ревизий
```

Данные — зеркало клиентских таблиц плюс `userId`, `rev`, `updatedAt`, `deletedAt`, с индексом
`(userId, rev)` под запрос дельты. Блобы: `blobs(sha pk, userId, size, createdAt)`, байты — файлами
на диске (`data/blobs/aa/bb/<sha>`), не в базе: SQLite-файл должен оставаться маленьким и быстро
копироваться при бэкапе.

`passwordHash` — nullable: пользователь, зарегистрировавшийся по одноразовому коду, пароля не имеет,
и это нормальное состояние, а не «незаполненное поле».

Tombstones и осиротевшие блобы чистит сборщик мусора через 30 дней — по расписанию, не в горячем
пути.

## Авторизация

Веб живёт на `olluorg.github.io`, расширение — на `chrome-extension://<id>`. Это разные origin,
поэтому httpOnly-cookie отпадают: остаётся **Bearer-токен**.

- `POST /v1/auth/register` — email + пароль. Хеш — Argon2id.
- `POST /v1/auth/login` — email + пароль + `deviceId` → `{ access, refresh }`.
- `POST /v1/auth/code/request` — прислать одноразовый код на почту (он же passwordless-регистрация:
  если пользователя нет, он заводится при первом верном коде).
- `POST /v1/auth/code/verify` — email + код + `deviceId` → `{ access, refresh }`.
- `POST /v1/auth/refresh` — ротация refresh-токена.
- `POST /v1/auth/logout` — отзыв.
- Позже: `POST /v1/auth/oauth/google` — пишет в `identities`, данные не мигрируются.

**Код, а не magic link.** Ссылка из письма открывается в браузере, а войти нужно в расширении —
шестизначный код пользователь просто вставляет в поле. Один механизм на оба клиента.

Access-JWT (HS256, 15 минут, claims `sub` и `deviceId`) хранится в памяти; refresh — случайные
32 байта, в базе лежит только SHA-256 от него, при обмене ротируется, повторное использование
отозванного токена гасит всю цепочку. Хранилище на клиенте: `chrome.storage.local` в расширении,
`localStorage` в вебе (в вебе это уязвимо к XSS — принимаем осознанно; на этом и держится решение
не хранить в токене ничего, кроме идентификатора).

Rate-limit на `login` и `code/request` — по IP и по email, иначе одноразовый код перебирается.

CORS: белый список origin (Pages + id расширения), без `*`.

## Сервер: устройство

```kotlin
val db = createSqliteDatabase("stramus.db") {   // poolSize = 1, WAL, foreign_keys=ON — по умолчанию
    beforeStart { migrate(serverMigrations) }
}

fun Application.module() {
    install(Kormium) { manage(db) }
    install(StatusPages) { exception<KormiumException> { call, e -> call.respond(e.httpStatusCode(), …) } }
    routing {
        authenticate("jwt") {
            post("/v1/sync") { val delta = call.transaction(db) { … } ; call.respond(delta) }
        }
    }
}
```

Миграции — `kormium-migrate`: журнал `kormium_migrations`, контрольные суммы, вся пачка одной
транзакцией, `migrate(...)` безопасно звать на каждом старте.

**Оговорки к SQLite, которые надо принять сознательно.** Писатель ровно один (`poolSize = 1` —
дефолт `kormium-sqlite` именно поэтому), значит один инстанс сервера, без горизонтального
масштабирования; при десятках одновременных push'ей они выстроятся в очередь. Для личного менеджера
вкладок с сотнями пользователей этого достаточно с большим запасом. Бэкап — копия файла с
WAL-checkpoint (или Litestream в S3). Путь на Postgres остаётся открытым, если весь доступ к данным
идёт через DSL Kormium, а сырой SQL живёт только в миграциях — тогда переезд сводится к новому
набору миграций и другой фабрике базы.

## Синхронизация на клиенте

Движок — одна фоновая корутина с очередью и экспоненциальным бэкоффом. Триггеры: старт приложения,
возврат фокуса на страницу, локальная мутация (с debounce 3 с), таймер (раз в минуту; в расширении —
`chrome.alarms` в service worker). Push-канал (SSE) можно добавить позже, протокол от этого не
меняется — он только делает pull своевременнее.

Весь цикл (применение дельты + запись `sync_meta` + новый `lastRev`) идёт **одной локальной
транзакцией**: оборванный на середине синк не должен оставить базу в состоянии, где `lastRev` уже
новый, а строки — старые.

В UI: индикатор состояния (синхронизировано / есть несохранённые изменения / оффлайн / ошибка),
экран входа, и уведомление при появлении конфликтующей копии — молча плодить карточки нельзя.

## Этапы

1. **Клиент, без сервера.** `core` → KMP; дробный индекс; sync-колонки, `sync_meta`, `sync_state`,
   tombstones; миграция локальных баз. Тесты на JVM для `between()` и правил слияния. Наружу
   приложение не меняется.
2. **Сервер: аккаунты.** Ktor + kormium-sqlite + миграции; регистрация, вход паролем и кодом,
   refresh; CI (сборка + тесты через `testApplication`); docker-compose для локального запуска.
3. **Сервер: `/v1/sync`** + клиентский движок + экран входа и индикатор. Тут синхронизация впервые
   работает end-to-end — на секциях, коллекциях, карточках.
4. **Файлы.** `/v1/blobs`, `blobSha` в карточках, квоты и лимиты.
5. **Хвосты.** `usage`/`action_usage` (со слиянием по максимуму), иконки, сборщик мусора, Google
   OAuth, SSE.

Иконки (`favicons`) намеренно в самом конце: это кэш, который второе устройство восстанавливает само
за секунды, а весит он больше всего остального вместе взятого. Синхронизировать — можно, но первым
это делать незачем.
